# 消息如何到达 Agent

Relanox 是连接原生消息账号与云端 Agent 的 Go 服务。程序通过显式构造函数组合
通道、Agent、存储、语音和观测组件，共享接口位于 `internal/model`。
配置由 `internal/config` 管理，公共 HTTP 传输实现位于 `internal/transport`。

## 原生接入

通道在能够保留取消、I/O 边界和原生标识符的地方使用平台或社区 SDK。
接收确认、授权、检查点、重试与最终回复状态由 Relanox 管理。依赖版本固定在
`go.mod`；各通道的 SDK 与保留协议实现见[英文架构说明](../en/architecture.md#native-sdk-boundaries)。

dot、Grok 和 Muse 使用官方 MCP Go SDK。dot 事件使用 Standard Webhooks 签名，
Muse 在 Noise XX 上保留自己的帧格式与 nonce 限制，Grok 使用 Cursor Routine
webhook。配置步骤与确认语义见[云端 Agent](agents.md)。本地协议测试不等于真实账号验证。

## 接收与授权

原生输入先经过认证，确定账号、发送者以及准确的会话或线程。账号允许列表与匹配的
binding 决定是否接收，binding 的允许列表可以进一步收窄权限。

核心在同一事务中保存不可变的端点归属、原始正文、媒体以及已确定的处理计划，
持久化成功后才返回接收确认。平台事件 ID 用于去重。后续配置修改不会把已经接受的
任务转交给另一个 Agent。

腾讯语音识别等预处理结果单独保存，不改变路由和原始媒体。worker 使用租约令牌与
版本领取有界任务；通知 Agent 后再记录结果。可能已经产生远端副作用的失败保留为
未知结果，只有原生操作明确支持安全幂等时才能自动重试。

## 查询与回复

Agent 身份限定到当前获准访问的端点。每次查询状态、消息、媒体或发送回复，都重新
检查当前账号归属与授权。历史记录在数据库中完成过滤、排序与边界限制；等待处理的
请求按接收时间及请求 ID 稳定排序。

每次发送具有独立持久化的目标与端点归属、有序的原生分块和幂等键。进度回复不会
完成请求；一个请求最多关联一次最终回复，所有文本与媒体分块确认发送后才完成。
企业微信的被动回复在等待平台取回期间保持 pending，发送时会重新检查原生能力的有效期。

## 存储与恢复

SQLite 和 PostgreSQL 共用 Ent schema、生成的查询构建器、事务 API 和版本化迁移。
租约领取、状态结算、比较并交换、媒体预算和队列写入保持原子性。
不兼容的旧版数据库会被拒绝，程序不会静默重建或丢弃数据。

恢复测试使用真实存储，覆盖重新打开数据库、结果不明、租约隔离、保留期与授权变化。
备份与排查步骤见[运维](operations.md)。

## 媒体与安全边界

媒体由 Relanox 持有，限定到账号，保存不可变元数据和校验和，并与所属消息原子提交。
平台下载地址只作为临时输入。预览图共享所属账号与媒体预算；内容过期后仍可保留用于
识别幂等发送的元数据。各平台的长度单位、图片顺序和收发能力差异保持原生语义。

HTTP 请求传递 context 取消、超时和响应大小限制。远端下载检查私有地址及 DNS 重绑定，
显式本地桥接使用配置的私网主机允许列表。公开原生回调与 MCP 监听、私有管理监听分别运行。
凭据从环境变量或文件引用在使用时解析；普通日志不记录消息正文或解析后的凭据。
