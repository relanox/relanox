# 消息如何到达 Agent

Relanox 将你的聊天账号连接到已有的 dot、Grok Bot 或 Muse。每个已绑定会话或话题都是一个授权 channel。来信携带来源 channel，Agent 向有权访问的 channel 发送消息。

## 跟着一条消息看流程

1. **用户发送消息。** 渠道连接从平台接收文字和支持的附件。
2. **Relanox 检查使用权限。** 发送者必须在账号的允许名单中，会话也必须绑定到一个 Agent。线程需要自己的匹配绑定；绑定还可以设置更小的允许名单。
3. **Relanox 保存消息。** 在 Core 确认接收之前，文字、附件、来源 channel 和接收 Agent 会保存到 SQLite 或 PostgreSQL。同一个平台事件重复到达时，会自动识别。
4. **可选中间件预处理消息。** 配置的中间件在转发前依次执行，例如语音插件追加识别文字；原消息和附件保持完整。未配置中间件则直接继续。
5. **Agent 收到通知。** Relanox 将消息、来源 channel 和附件信息发送给 dot、Grok 或 Muse。Agent 可以读取附件，并在自己的服务中准备回答。
6. **Agent 向 channel 发送消息。** 它选择来源 channel，或从 `relanox_status` 选择其他授权 channel，提交文字或支持的媒体。Relanox 保存独立的投递记录，按平台长度限制拆分长文字，再发送并记录结果。

原生平台允许时，Agent 也可以在收到来信之前向授权 channel 发送消息。`relanox_status` 列出可用 channel，并说明缺少的平台上下文或已过期的发送窗口。渠道允许多次回复时，Agent 可以先发一条进度说明，再发最终答案。企业微信 HTTP 回调每条来信只允许一次回复，因此该模式只发送最终答案。收到问题后，Agent 需要时间处理；完成后，回复会出现在原会话。回复迟迟没有出现时，参阅[消息状态与恢复](reference/core.md)。

## 重启之后会怎样？

已保存的工作保留在配置的数据库中。Relanox 再次启动后，会继续处理等待通知或发送的消息。请将 SQLite 文件放在持久存储上，或使用持久化的 PostgreSQL 数据库。

请保持服务运行，以便及时接收新消息。遇到中断后，先检查渠道连接，再把仍需回答的问题重新发送。

## 旧消息会发到哪里？

已接收消息保留当时选择的 Agent 端点。每条已入队投递分别保存自己的目标和端点，修改绑定不会重定向这些投递。新发送使用当前绑定：移除或重新分配 channel 后，原 Agent 不再有权访问它及其媒体。

Channel ID 根据绑定和 Agent 端点生成。使用当前 status 或来信 `source.channel.id` 中的值，不要根据消息 ID 构造它。端点归属或配置变化可能改变 channel ID。同一机器人身份下轮换凭据后，更新环境变量并重启服务，已保存投递会使用更新后的凭据。

## 需要运行哪些服务？

准备一台运行 Relanox 的电脑或服务器，以及一个可用的 dot、Grok Bot 或 Muse。开始使用时可选择 SQLite，数据保存在本机文件中；也可以连接 PostgreSQL。有些渠道需要公开的 HTTPS 地址来接收回调或提供媒体下载；另一些渠道主动连接平台。各[渠道指南](channels/index.md)说明了具体要求。

三种云端 Agent 都需要公网可访问的 HTTPS 地址连接 MCP，包括主动连接平台的渠道。

服务另有一个本机管理地址，用于健康检查和指标采集。请保持该地址私有。标准运行日志不包含消息正文或凭据；管理命令仅在你明确要求时显示消息正文。
