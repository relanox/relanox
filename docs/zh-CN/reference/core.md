# 消息状态与恢复

消息延迟、回复重复，或不确定是否应该重试发送时，可以查阅本页。[运行维护](../operations.md)提供了查看和恢复消息的命令。

## 已接收、已接受与已送达有什么区别？

Relanox 先保存来信及其来源 channel，再通知选定的 Agent。Agent 可以在准备好答案之前接受通知。每次向授权 channel 发送消息都会创建独立的投递记录，无需先有一条来信。

| 状态            | 含义                                   | 建议操作                            |
| --------------- | -------------------------------------- | ----------------------------------- |
| 通知 `due`      | 输入等待通知或再次尝试。               | 检查 Agent 连接和最近错误。         |
| 通知 `accepted` | Agent 已接受通知。                     | 没有回复时，检查 Agent 自身的服务。 |
| 发送 `pending`  | 已保存的回复尚未全部发完。             | 检查渠道连接和重试错误。            |
| 发送 `sent`     | 回复的所有部分都已发送，并记录了回执。 | 无需恢复。                          |
| `rejected`      | 永久错误或重试次数用尽，处理已经停止。 | 修复原因后再手动重新入队。          |
| `unknown`       | 无法确认远端操作是否已经发生。         | 重试前先检查远端会话或 Agent。      |

Agent 收到的 `queued` 表示回复已保存，不是聊天平台的送达回执。

## 哪些情况会自动重试？

已知的临时失败，例如平台明确报告限流或可重试的服务错误，会延迟重试。默认最多尝试八次；等待时间从一秒逐步增加到五分钟。可重试的响应也可以指定该范围内的等待时间。标准 CLI 使用上述默认重试设置。

如果调用超时，但请求可能已经到达远端，再发一次就可能重复。Relanox 会把这类不确定结果记为 `unknown`，停止自动尝试。

Agent 接受通知后，不会因为迟迟没有回复而自动再次收到通知。将输入重新入队会再次通知 Agent，不会取消它之前的工作。

## 为什么后面的回复还在等待？

同一个 channel 的消息按保存顺序发送。长文字会拆成符合平台限制的多段，然后发送附件。前一条投递处于等待状态时，会阻挡该 channel 后续的消息。不确定状态也会阻挡后续消息，但 QQ 除外：后续回复可以继续，不确定的投递仍保留回执，需要显式恢复。恢复这条 QQ 投递时，剩余部分可能晚于较新的回复送达。前一条投递被拒绝后，后续消息可以继续。

不同 channel 可以独立处理，即使它们使用同一个 Agent。

## 怎样避免重复消息？

同一个平台事件重复到达时，会自动识别。Agent 发送时不提供 `idempotencyKey`，每次都会创建新消息，即使内容与之前相同。

重试时使用相同的键、channel、文字和有序附件，Relanox 会返回原投递 ID；用同一个键提交不同内容会返回 `conflict`。每次新的发送意图使用新键，已经返回 `queued` 的发送不要换键重试。Agent 可以把该 `deliveryId` 传给 `relanox_status` 查询投递情况，无需再次发送。

如果你编写集成，可靠重试以及有意发送重复内容的方法见[扩展接入](sdk.md)。

## 恢复之前要确认什么？

先查看当前记录，修复连接、凭据或平台限制。结果为 `unknown` 时，先确认消息是否已经到达。恢复需要填写记录当前的版本；恢复不确定结果还需要明确接受可能重复发送的风险。

已经发送了一部分的回复会从未完成的部分继续，并保留前面部分的回执。重启服务可以继续已保存的工作，但不会自行消除远端结果的不确定性。恢复命令见[运行维护](../operations.md)，定位失败环节可参考[日志与监控](observability.md)。

## 将最终回复关联到来信

回复带有 `requestId` 的来信时，在一次 `relanox_send_message` 调用中提交完整文本、有序媒体和 `reply: { requestId, kind: "final" }`。进度消息使用 `kind: "progress"`。关联回复必须使用来信的源频道及当前授权端点；原生回复上下文取自这条来信。主动发送省略 `reply`。

使用 `relanox_status` 的 `requestId` 参数，或查看 `relanox_read_messages` 返回的 `reply`。`awaiting_final` 表示尚无最终回复入队；入队后的 `pending`、`sent`、`rejected`、`unknown` 对应最终回复的投递状态。只有 `sent` 表示平台已接受全部文本和媒体分片，不代表收件人已读。读取、进度消息和事件接收成功都不会完成来信。

每条来信只能关联一条最终投递。相同最终回复即使换发送键也会返回原投递；修改内容返回 `conflict`。失败的最终回复应通过原投递 ID 恢复。不关联来信的发送保持原有幂等键行为。保留期清理可能移除来信内容；此时 `expired` 表示这条尚未回答的来信已无法补取正文。

## 补取未完成消息

`relanox_read_messages` 已支持按 `requestId` 读取一条来信或读取最近消息。使用 `pending: true`，可在现有读取能力上筛选正文仍保留且最终回复尚未全部发送的来信，按接收时间从旧到新返回。后续调用携带 `nextCursor`，直到不再返回游标；最后一页恰好满额时，可能还需读取一个空页。默认每页 5 条，最多 20 条。不要将 `requestId` 与未完成分页组合使用。

处理前检查 `reply.status`：仅对 `awaiting_final` 作答；`pending`、`rejected`、`unknown` 应检查已有 `deliveryId`。发送前再次查询状态。读取是状态快照，不会认领任务、重发事件或确认处理完成。并发最终回复通过来信关联去重；答案不同则冲突。下一次恢复从第一页重新扫描。

已有投递继续通过 worker 或现有 CLI `requeue --kind delivery` 恢复，仍检查版本，未知结果仍需显式确认重复风险。已有最终回复的来信现在拒绝请求级 requeue，返回 `conflict`，应恢复原投递。CLI 状态同时展示来信到最终投递、投递到来信的关联。

现有保留期策略保持不变：已清理正文的来信不进入未完成分页。已知来信 ID 可通过 `relanox_status` 区分 `expired` 或尚未完成的最终投递。这项能力供 dot 运行或被手动调用时补取消息，无法强制 dot 在接受事件后唤醒。
